# Database Implementation Plan

## Scope

This document defines the PostgreSQL schema and the SQLAlchemy/Alembic implementation. PostgreSQL is responsible for durable storage, referential integrity, basic value constraints, uniqueness, and query performance. Authorization, 48-hour eligibility, and legal state transitions are additionally enforced in backend transactions.

## Conventions

- PostgreSQL 16+; schema `public`.
- Table names are plural `snake_case`.
- Primary keys are UUIDs generated by the application with UUIDv4.
- All timestamps are `timestamptz`, stored in UTC, and non-null unless the lifecycle requires null.
- The application supplies timestamps from one injectable UTC clock per transaction.
- Money is `bigint` cents to avoid decimals and permit safe aggregation.
- SQLAlchemy models use `Mapped[...]`, `mapped_column`, and explicit relationships.
- Alembic migrations are the only supported way to alter shared schemas.

## Schema

### `users`

| Column | PostgreSQL type | Null | Default / constraint |
|---|---|---:|---|
| `id` | `uuid` | no | primary key |
| `email` | `varchar(320)` | no | normalized lowercase value, unique |
| `password_hash` | `text` | no | no plaintext constraint is possible; application-owned |
| `created_at` | `timestamptz` | no | application UTC time |
| `updated_at` | `timestamptz` | no | application UTC time |

Constraints and indexes:

- `uq_users_email` unique B-tree index on `email`.
- `ck_users_email_not_blank`: `length(btrim(email)) > 0`.
- The service normalizes with Unicode trim plus lowercase before lookup and insert. V1 does not perform provider-specific dot/plus normalization.

### `sessions`

| Column | PostgreSQL type | Null | Default / constraint |
|---|---|---:|---|
| `id` | `uuid` | no | primary key |
| `user_id` | `uuid` | no | FK to `users.id` |
| `session_token_hash` | `char(64)` | no | unique lowercase SHA-256 hex digest |
| `expires_at` | `timestamptz` | no | must be after creation |
| `created_at` | `timestamptz` | no | application UTC time |
| `last_used_at` | `timestamptz` | no | initial value equals `created_at` |

Constraints and indexes:

- `fk_sessions_user_id_users` with `ON DELETE CASCADE`.
- `uq_sessions_token_hash` unique index for session resolution.
- `ix_sessions_user_id` for account/session cleanup.
- `ix_sessions_expires_at` for scheduled deletion of expired sessions.
- `ck_sessions_expiry`: `expires_at > created_at`.
- `ck_sessions_last_used`: `last_used_at >= created_at`.

### `impulse_purchase_entries`

| Column | PostgreSQL type | Null | Default / constraint |
|---|---|---:|---|
| `id` | `uuid` | no | primary key |
| `user_id` | `uuid` | no | FK to `users.id` |
| `item_name` | `varchar(200)` | no | trimmed, nonblank |
| `price_cents` | `bigint` | no | `1..999999999999` |
| `reason_wanted` | `varchar(2000)` | no | trimmed, nonblank |
| `status` | `varchar(16)` | no | `waiting`, `saved`, or `purchased` |
| `comment` | `varchar(4000)` | yes | null or trimmed/nonblank |
| `created_at` | `timestamptz` | no | start of wait period |
| `checked_in_at` | `timestamptz` | yes | set on resolution |
| `updated_at` | `timestamptz` | no | last mutation time |

Constraints:

- FK `user_id -> users.id` with `ON DELETE CASCADE`.
- `ck_entries_status`: status in the three stored values.
- `ck_entries_item_name_not_blank` and `ck_entries_reason_not_blank`.
- `ck_entries_comment_not_blank`: comment is null or `length(btrim(comment)) > 0`.
- `ck_entries_price`: `price_cents BETWEEN 1 AND 999999999999`.
- `ck_entries_lifecycle`: waiting implies `checked_in_at IS NULL`; saved/purchased imply `checked_in_at IS NOT NULL`.
- `ck_entries_checked_after_created`: checked-in time is null or not before creation.
- `ck_entries_updated_after_created`: updated time is not before creation.

Indexes:

- `ix_entries_user_status_created` on (`user_id`, `status`, `created_at DESC`) for dashboard grouping.
- `ix_entries_user_status_checked` on (`user_id`, `status`, `checked_in_at DESC`) for filtered statistics and resolved lists.
- Normal owned reads use both primary key and `user_id`. The backend may perform a minimal ID-only existence check after a miss solely to distinguish the contractually required `403` from `404`; it must never return the row's data.

Do not create or persist a `needs_check_in` column. The eligible time is `created_at + interval '48 hours'` and is serialized by the backend.

### `opportunity_cost_examples`

| Column | PostgreSQL type | Null | Default / constraint |
|---|---|---:|---|
| `id` | `uuid` | no | primary key |
| `user_id` | `uuid` | no | FK to `users.id` |
| `label` | `varchar(120)` | no | trimmed, nonblank |
| `unit_name` | `varchar(80)` | no | trimmed, nonblank |
| `dollar_value_cents` | `bigint` | no | `1..999999999999` |
| `created_at` | `timestamptz` | no | application UTC time |
| `updated_at` | `timestamptz` | no | application UTC time |

Constraints and indexes:

- FK `user_id -> users.id` with `ON DELETE CASCADE`.
- Check constraints for nonblank label/unit, positive bounded dollar value, and `updated_at >= created_at`.
- `ix_opportunity_cost_examples_user_created` on (`user_id`, `created_at`, `id`) for stable listing.
- Duplicate labels are allowed in V1 because examples may intentionally use different unit values.

## SQLAlchemy Model Behavior

- Keep persistence models separate from Pydantic API schemas.
- Use `lazy="raise"` relationships to prevent accidental N+1 queries.
- Do not use model event hooks for business rules or timestamps; services explicitly assign changes.
- Set `expire_on_commit=False` on async sessions and refresh only where database-generated data is required.
- Define enum values in Python with `StrEnum`, while retaining a database check constraint so adding a value requires a reviewed migration.
- Never serialize ORM instances directly from routers; map them to response schemas.

## Query Design

### Dashboard list

One scoped query selects entries for `user_id` and orders deterministically. The repository partitions returned rows using the same request-scoped `now`:

```text
needs_check_in: status=waiting and created_at <= now-48h
waiting:        status=waiting and created_at > now-48h
saved:          status=saved
purchased:      status=purchased
```

Ordering:

- Needs check-in: `created_at ASC, id ASC` (oldest first).
- Waiting: `created_at ASC, id ASC` (soonest eligible first).
- Saved/Purchased: `checked_in_at DESC, id DESC` (most recently resolved first).

For expected V1 volume, one query plus in-process partitioning is simpler than four round trips. Add pagination before unbounded per-user growth becomes material.

### Statistics

Use one conditional aggregate scoped by user and `checked_in_at >= range_start` when a start exists:

```sql
SELECT
  COALESCE(SUM(price_cents) FILTER (WHERE status = 'saved'), 0),
  COUNT(*) FILTER (WHERE status = 'saved'),
  COUNT(*) FILTER (WHERE status = 'purchased')
FROM impulse_purchase_entries
WHERE user_id = :user_id
  AND status IN ('saved', 'purchased')
  AND (:range_start IS NULL OR checked_in_at >= :range_start)
  AND checked_in_at < :range_end;
```

All ranges are half-open `[start, end)`. `range_end` is the request clock. `this_month` begins at 00:00 UTC on day one of the current UTC month. Rolling ranges subtract 3, 6, or 12 calendar months from `range_end`; `all_time` has no start. These semantics must be exposed in backend tests and kept consistent.

### Atomic check-in

Lock the owned row with `SELECT ... FOR UPDATE`. Recheck status and eligibility after the lock, then update status, comment, `checked_in_at`, and `updated_at` in the same transaction. This prevents two requests from both succeeding.

## Migration Plan

Initial revision order within one migration:

1. Create `users`.
2. Create `sessions` and its indexes.
3. Create `impulse_purchase_entries` and its indexes.
4. Create `opportunity_cost_examples` and its index.

The downgrade drops objects in reverse dependency order. Before merge:

- Run `alembic upgrade head` on an empty database.
- Inspect generated SQL; name every constraint and index explicitly.
- Run `alembic downgrade base`, then upgrade again.
- Run model metadata versus migration drift detection in CI.

Future migration rules:

- Never edit a migration already applied to a shared environment.
- Separate large data backfills from constraint enforcement when deployment safety requires it.
- New non-null columns on populated tables require a staged default/backfill/not-null sequence.
- Migrations must not import mutable application model definitions.

## Data Retention and Cleanup

- Expired sessions are invalid immediately at read time even before physical deletion.
- A scheduled task may delete sessions where `expires_at < now()` in indexed batches.
- Resolved entries are not user-deletable in V1.
- Deleting an account is not a V1 API operation; if added, cascading behavior must be surfaced as an explicit destructive user action.
- Database backups and restore testing are deployment responsibilities.

## Database Tests

Test against PostgreSQL and cover:

- Unique normalized email and unique token hash.
- Every check constraint with a failing insert/update.
- User deletion cascades to all owned rows.
- Exact 48-hour dashboard boundary.
- Stable ordering for equal timestamps.
- Each stats range boundary and zero-result `COALESCE` behavior.
- Large cent totals do not overflow.
- Concurrent check-in yields one success and one lifecycle conflict.
- Migration upgrade, downgrade, and re-upgrade from an empty database.

## Acceptance Checklist

- Schema matches all API fields without storing derived buckets.
- Every foreign key, constraint, and performance index is explicitly named.
- All ownership queries require `user_id`.
- Migration and ORM metadata agree.
- Query plans use the intended indexes with representative seeded data.
- No raw password or session token can be persisted.
